# ipsearch — i-PRO 同軸-LANコンバーターの IP 探索ツール

対象機種: **WJ-PR204UX** (レシーバー側4ch) / WJ-PR201UX / WJ-PC200UX

設定用 IP を見失った i-PRO 同軸-LANコンバーターを、PC (Mac / Linux) と
直結したまま ARP スイープ / パッシブ待ち受けで探し出す単一ファイルの CLI ツール。
外部ライブラリ不要 (macOS / Linux + python3 標準ライブラリのみ)。

インターフェース名は環境で読み替える (macOS は `en5` 等、Linux は `eth0` 等)。
以下の例は Linux の `eth0` で記載する。

## クイックスタート

```sh
# 1. 機器と PC を Ethernet で 1 対 1 直結し、インターフェース名を確認
python3 ipsearch.py ifaces

# 2. おまかせ実行 (待ち受け -> 段階的スイープ -> HTTP 同定)
sudo python3 ipsearch.py auto -i eth0
```

見つかった IP・設定画面の URL・既定の認証情報 (`WJ-PR204` / `999999`) と、
そこへ到達するまでの手順が出力される。詳細は以下。

## なぜ必要か

これらの機種は、設定画面の `Option` から設定用 IP アドレスを変更できるが、
**工場出荷時に戻す初期化(リセット)手段が取扱説明書に一切記載されていない。**
リセットスイッチも無く、設定画面の `Restart` にある `Reset` ボタンは再起動でしかない。
取扱説明書の注意書きも「新しいIPアドレスを忘れないように、必ずメモしてください」
とあるだけで、忘れた場合の救済手順が無い。

したがって IP を見失うと、**総当たりで探す以外に Web UI へ到達する手段が無い。**

本ツールは機器のネットワーク端子に直結した Mac から **ARP スイープ** を行う。
ARP は L2 のプロトコルなので、こちら側の IP 設定と相手の IP 設定が噛み合って
いなくても応答が返る。つまり相手が 10.x でも 172.x でも 192.168.x でも、
IP を合わせずに発見できる。応答したホストには HTTP を投げ、認証レルム
(`Basic realm="WJ-PR204"`) で対象機器かどうかを同定する。

## 工場出荷時の値 (取扱説明書 PGQX2622ZAJ1 より)

| 項目 | 値 |
| --- | --- |
| IP アドレス | `192.168.249.249` (レシーバー側) |
| サブネットマスク | `255.255.255.0` |
| ユーザー名 | `WJ-PR204` (機種名と同じ) |
| パスワード | `999999` |
| 設定画面 | `http://192.168.249.249/` |

重要な仕様: **設定画面は本機のネットワーク端子に直結した PC からのみ表示できる。**
スイッチングハブ越しでは開けないので、必ず Mac と機器を Ethernet ケーブルで
1 対 1 で繋いでから実行すること。

## 動作条件

- macOS / Linux 対応。L2 の生フレーム送受信をプラットフォームで切り替える
  - macOS : BPF (`/dev/bpfN`) を直接使用
  - Linux : AF_PACKET raw socket を使用 (OpenBlocks IoT DX1 等の機器上でも動作。VLAN サブIF も可)
- Python 3.8+ (システム標準の `python3` でよい。**外部ライブラリ不要**)
- Linux では `ip` コマンド (iproute2) を使う (インターフェース列挙・一時 IP 付与)
- raw パケット送受信のため **sudo / root 必須**

### 注意: 複数 NIC を持つホストでの取りこぼし

対象と**同じサブネットの IP を「別の NIC も」持っている**と、機器を見つけ損ねることがある。
ARP スイープ自体は `-i` で指定した NIC から raw で送るので効くが、その後の **HTTP に
よる機種同定**は OS のソケット経由なので、OS のソースアドレス選択・ARP 応答が別 NIC 側に
偏ると別経路から出てしまい、対象を取りこぼす(応答はしたのに `WJ-PR204` 等として同定
できない、あるいは 401/200 が返らない)。

実例: Mac に en0(`172.31.16.156`)と en5(`172.31.16.100`)の両方が同一 /24 に居る状態で
`-i en5` を指定しても、HTTP 判定が en0 経由になり対象コンバーターを取りこぼした。**探索対象の
セグメントに関わる NIC は 1 つだけ有効**にしてから実行すること(不要な NIC は
`sudo ifconfig <if> down` / Linux は `sudo ip link set <if> down` で落とす)。

## 使い方

### 0. 事前確認

```sh
# インターフェース一覧
python3 ipsearch.py ifaces

# ツール自体が正常に動くかを既知のネットワークで確認 (機器を繋ぐ前に一度)
sudo python3 ipsearch.py selftest -i en5
```

`selftest` は指定インターフェースの所属サブネットを ARP probe で掃き、
自分以外に 1 台でも応答すれば PASS。ここが通らなければ配線か
インターフェース指定が間違っている。

### 1. おまかせ実行

```sh
sudo python3 ipsearch.py auto -i en5
```

以下を順に実行する。

1. **パッシブ待ち受け (60秒)** — Enter を押してから待ち受けが始まるので、その間に
   機器の電源を入れ直す。起動時の Gratuitous ARP や DHCP DISCOVER の送信元から
   IP が判明する。**こちらから宛先 IP を当てる必要が無いので、機器がどの IP 帯に
   設定されていても効く唯一の手段**。最も速く、最も確実。
2. **段階的 ARP スイープ** — `factory` (192.168.249.0/24) →
   `common` (192.168/16, 172.16/12, 169.254/16) → `all` (+10/8)。
   応答があった時点で以降の段を省略する。
3. **HTTP 同定** — 応答した各 IP に対し、一時的に同一サブネットの IP を
   インターフェースに生やしてから `http://<ip>/` を取得し、認証レルムで機種を
   判定する。対象機種と分かったホストにだけ `WJ-PR204` / `999999` を試す。
   エイリアスは終了時に外す。

見つかると、設定画面を開くまでの手順（Mac に振るべき IP、URL、認証情報）を
そのまま出力する。

### 2. 個別に実行する場合

```sh
# 待ち受けだけ (この間に機器の電源を入れ直す)
sudo python3 ipsearch.py sniff -i en5 --seconds 60

# レンジを指定してスイープ
sudo python3 ipsearch.py scan -i en5 --ranges factory
sudo python3 ipsearch.py scan -i en5 --ranges common
sudo python3 ipsearch.py scan -i en5 --ranges all --pps 30000
sudo python3 ipsearch.py scan -i en5 --ranges 10.0.0.0/8 192.168.0.0/16

# 既に IP の当たりが付いている場合、HTTP 同定だけ行う
sudo python3 ipsearch.py verify -i en5 192.168.249.249
```

## 所要時間の目安

`--pps 20000`、`--retries 2` (既定) の場合。

| レンジ | アドレス数 | 目安 |
| --- | --- | --- |
| `factory` (192.168.249.0/24) | 256 | 1 秒未満 |
| `common` (192.168/16 + 172.16/12 + 169.254/16) | 約 118 万 | 約 2 分 |
| `all` (上記 + 10/8) | 約 1790 万 | 約 30 分 |

`--pps` は上げれば速くなるが、取りこぼしが増える。既定の 20000 で足りないときは
`--pps 5000 --retries 3` のように落として確実性を取る。

## 主なオプション

| オプション | 説明 |
| --- | --- |
| `-i, --interface` | 機器と直結しているインターフェース。省略時は active な物理 IF が 1 つだけなら自動選択 |
| `--ranges` | `factory` / `common` / `all` またはCIDR を複数指定 |
| `--pps` | ARP 送信レート (既定 20000) |
| `--retries` | スイープ回数 (既定 2)。パケットロス対策 |
| `--spa` | ARP の送信元 IP。下記参照 |
| `--mac` | 機器の MAC が分かっている場合の絞り込み |
| `--out` | 結果を JSON で書き出す |
| `--no-http` | HTTP 同定を行わず、ARP 応答の列挙だけ行う |
| `--no-alias` | HTTP 同定時に一時 IP エイリアスを追加しない |
| `--try-creds` | 機種を同定できなかった 401 ホストにも既定パスワードを試す |
| `-y, --yes` | 共有ネットワーク警告に対する確認を省略する |

### `--spa` (ARP の送信元 IP) の使い分け

- `probe` (既定) — `0.0.0.0` を名乗る (RFC 5227 の ARP probe)。相手の ARP
  テーブルを汚さない。ほとんどの実装はこれに応答する。
- `peer` — ターゲットと同じ /24 のアドレスを名乗る。サブネット外からの ARP に
  応答しない硬い実装でも確実に返ってくるが、**送信元 IP を詐称する**ため
  相手の ARP キャッシュを汚染する。直結環境でのみ使うこと。
- 任意の IPv4 — 固定の送信元アドレスを使う。

まず既定の `probe` で試し、見つからなければ `--spa peer` を試す。

## 注意 (共有ネットワークでの誤爆防止)

- **業務ネットワークに繋いだまま広いレンジを掃かないこと。** 機器と Mac を
  1 対 1 で直結したポートで使うこと。
- 対象インターフェースがデフォルトルートを持つ、または 169.254 以外の IP が
  付いている場合、「共有ネットワークの疑いあり」として警告する。さらに
  `--spa peer` または 4096 アドレス超のスイープを指定した場合は対話確認を要求する
  (`--yes` で省略可)。
- 既定パスワードの試行は、認証レルムで対象機種と判定できたホストにしか行わない。
  無関係な機器へのログイン試行を避けるため。`--try-creds` で緩められるが、
  共有ネットワークでは使わないこと。

## 見つかった後

1. PC に、機器と同じサブネットの IP を振る
   ```sh
   # macOS
   sudo ifconfig en5 alias 192.168.249.100 netmask 255.255.255.0
   # Linux
   sudo ip addr add 192.168.249.100/24 dev eth0
   ```
2. ARP テーブルを消す (`sudo arp -d -a` / Linux は `sudo ip neigh flush all`)
   (取扱説明書にも、前に繋いだコンバーターの arp エントリが残っていると
   設定画面が開かないことがあると記載されている)
3. ブラウザで `http://<見つかったIP>/` を開き、`WJ-PR204` / `999999` で認証
4. `Option` 画面で IP アドレスを確認・変更し、**今度こそ控えておく**
5. 作業後にエイリアスを外す
   ```sh
   # macOS
   sudo ifconfig en5 -alias 192.168.249.100
   # Linux
   sudo ip addr del 192.168.249.100/24 dev eth0
   ```

## 見つからないとき

1. `sudo python3 ipsearch.py selftest -i <IPの付いたIF>` が PASS するか。
   FAIL ならツール側 (L2 送受信) の問題。
2. 機器の LAN ランプが緑点灯しているか (オレンジ点灯 = リンクが上がっていない)
3. `-i` のインターフェース指定が正しいか (`ipsearch.py ifaces` で確認)
4. `--spa peer` に切り替えて再試行
5. `--pps 5000 --retries 3` で取りこぼしを減らす
6. `--ranges all` で RFC1918 全域を掃く
7. **対象と同じサブネットの IP を別 NIC も持っていないか**を確認する。
   応答ホストには出るのに機種同定できない (HTTP が返らない/★が付かない) 場合はこれを疑う。
   探索対象に関わらない NIC は落としてから再実行する (上記「複数 NIC を持つホストでの取りこぼし」参照)

### ARP スイープの原理的な限界

ARP スイープは**宛先 IP を総当たりする**方式なので、IPv4 全空間 (43億) は掃けない。
設定用 IP が RFC1918 外 (グローバルアドレス帯など) に設定されていると、
`--ranges all` でも当たらない。

この場合に効くのは**パッシブ待ち受けだけ**。機器が自発的に出すフレームの
送信元アドレスを見るので、どの IP 帯だろうと関係なく判明する。

```sh
sudo python3 ipsearch.py sniff -i en5 --seconds 180
```

Enter を押すと待ち受けが始まるので、その間に機器の**電源を入れ直す**。
起動直後の Gratuitous ARP / DHCP DISCOVER が最も期待できる。
1 回で駄目なら待ち受け時間を延ばして数回繰り返すこと。
